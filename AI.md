Logged as the build goes.

## M0 — plan + docs

Used Claude to read the assignment brief, look at an existing RN project for architecture reference, and draft the build plan now in PLAN_README.md — data model, streak/freeze state machine, screen breakdown, milestone order, plus the mockups used to sanity-check the UI before coding.

## M1 — scaffold + native linking

Scaffolded with the React Native community CLI at RN 0.87.0, then matched nivo's exact dependency versions by hand in package.json. Caret ranges on react-native-reanimated/react-native-worklets pulled in a mismatched pair (reanimated 4.7.x wants worklets 0.13.x); pinned both to the exact versions nivo's lockfile resolved to instead.

Hit a real native issue on first simulator run: the stock RN template's AppDelegate creates its own UIWindow directly, but the Xcode 27.2 / iOS 26 SDK this machine builds against requires the UIScene app lifecycle — the app failed to launch with "UIScene life cycle is required for apps built with this SDK." Fixed by adding UIApplicationSceneManifest to Info.plist and writing a SceneDelegate.swift that hosts the window instead, and had to register that new file by hand in the Xcode project since this project doesn't use Xcode's synchronized-folder groups. Worth remembering this will likely apply on the real device build too.

## M2 — mock layer + navigation shell

Pinning typescript to nivo's exact 5.0.4 (done in M1 to match the reference project) turned out to be wrong: @react-native/typescript-config@0.87.0 references the `es2024.promise` lib, which doesn't exist before TypeScript 5.5-ish, so `tsc --noEmit` failed outright with every JSX element reported as invalid — a confusing error that had nothing to do with the actual navigation/store code being added. nivo likely has this same latent breakage and never notices because its scripts never run `tsc` directly. Fixed by using the RN CLI scaffold's own typescript version (^6.0.3) instead of copying nivo's pin — matching the reference project isn't automatically correct when the reference project itself doesn't exercise the thing being matched.

Also hit a Cocoapods deployment-target conflict after adding @react-native-async-storage/async-storage: its resource-bundle target ships `IPHONEOS_DEPLOYMENT_TARGET = 13.0`, below the 15.0+ range this Xcode/SDK combo allows, so the build failed before even reaching app code. RN's own `react_native_post_install` helper doesn't touch resource-bundle targets, so added an explicit loop in the Podfile's `post_install` to bump any pod target below `min_ios_version_supported` up to it.

Wrote the mock API layer, Zustand store, navigation shell, and three placeholder screens (Login/Home/Collection) directly rather than asking AI to design them from scratch, since the shapes were already decided in the plan — AI's role here was mostly typing speed and catching the two environment issues above. Verified the whole login → tabs → mock-data loop on the iOS Simulator by hand (tap coordinates had to be found empirically — the simulator control tool's points-to-pixel scaling was easy to get wrong by eye, and a few taps landed on the wrong element before the right coordinates were found).

## M4 — home swipe challenge

Built the swipe UI on `rn-swiper-list` as planned (`ChallengeSwiper` wrapping its `Swiper`), plus `CardFace`, `RarityOverlayLabel`, and `RevealOverlay`. On-device testing surfaced a real, reproducible library bug: the first card swipes away correctly, but the second card never becomes visible — confirmed on multiple fresh app launches, in both swipe directions, and after trying a smaller `prerenderItems` as a workaround. Data flow (progress count, streak, answers) kept working underneath; only the rendering of the second card onward was broken.

Rather than ship a UI that's provably broken past the first card, replaced `rn-swiper-list` entirely with a small custom implementation: `SwipeCard.tsx` (one card, one `Gesture.Pan`, shared values for translateX/Y, release-threshold classification into common/rare/holo) plus a thin `ChallengeSwiper.tsx` that just tracks which of the 8 cards is active and swaps it on answer. Removed the now-unused `rn-swiper-list` dependency. This was a deliberate build-order payoff: the plan's own risk section flagged "if the library misbehaves on a real device we can swap the internals without touching Home" — that's exactly what happened, and the one-paragraph custom version turned out simpler than fighting the library.

Verified the full 8-card run on-device after the rewrite: all three swipe directions, accurate correct/incorrect feedback per card, streak incrementing 12→13 on completion, the reveal overlay showing the unlocked card, and the new card appearing in the Collection count (12→13). Also noticed a LogBox warning banner that appeared only while `rn-swiper-list` was in use and disappeared once it was removed — never got the exact text (no debugger attached), but consistent with it being a library-side issue rather than our code.

## Post-M4 review — multiple fixes

Review of M1–M4 raised several real issues, addressed in one pass before M5:

- **Safe area, tab icons, header, Home layout reorder** — straightforward fixes, no surprises. Added a custom SVG icon set (matching nivo's own icon-system convention, not a vector-icons font) and a shared `AppHeader` (Pullday + date).
- **Container/view/hooks architecture reversed** — M2's call to skip nivo's container/view split and skip extracting data-fetching into hooks was explicitly overturned on review as the wrong call for this task, not a style preference. Retrofitted Login/Home/Collection into the full nivo-shaped folder (`container.tsx`/`view.tsx`/`type.ts`/`styles.ts`/`utils/useXxxQuery.ts`). First attempt at the hooks also over-engineered it with a shared generic `useFetch` wrapper; told directly that wasn't wanted — nivo's own hooks manage their `data`/`error`/`isLoading` state inline per hook, so that's what got built instead. Good calibration point: "take reference from X" means match X's actual pattern, not a reasonable-looking abstraction inspired by it.
- **Real data.sql, not generated fixtures** — asked to render the real ~2,000-card dataset instead of synthetic placeholder cards. Found data.sql wasn't anywhere on the machine; the user supplied the gist's direct raw-file link, which resolved it immediately. Wrote a one-time Python parser (`data-source/parse_cards.py`) handling SQL's `''`-escaped quotes and — a real gotcha — the fact that the file has **10 separate INSERT statements**, not one; a first-pass regex that assumed a single statement silently merged a later statement's `insert into cards (...) values` line in as if it were a data row and threw. Fixed by matching each statement independently. Output: 1,993 real cards (1,486 common / 314 rare / 193 holo), bundled as JSON into the app.
- **A real Metro/bundler puzzle** — introducing the real card data first via a two-file split (`data/cards.ts` computing `ALL_CARDS`, `mock/cards.ts` re-exporting it as `MOCK_CARDS`) produced a deterministic "Cannot read property 'length' of undefined" on every cold launch, with no import cycle anywhere in the dependency graph to explain it structurally. Ruled out stale Metro processes (found and killed a leftover instance still bound to port 8081 from an earlier milestone — worth remembering to actually verify `lsof -i :8081` is clear before trusting a "fresh" `react-native start`, rather than just assuming a `pkill` worked) and confirmed with `simctl terminate` that the error was fully reproducible on genuine cold starts, not a resumed stale process. Root cause was never fully pinned down (suspect something in how Metro resolves a `.json` default-import across that particular two-hop module boundary), but collapsing the two files into one — loading and mapping the JSON directly inside `mock/cards.ts` — made the problem disappear entirely. Noted as a real unknown rather than papered over: if this resurfaces, the fix is "don't split a JSON-backed data module across more than one file," not a deeper explanation.
- **Gesture-area/tab-bar touch conflict** — after the card data fix, testing the tab bar revealed taps near the bottom were instead being captured by the swipe card's gesture detector (visibly triggering tiny drags/swipes), even though the card's visual bounds shouldn't have reached that far down. Added `overflow: 'hidden'` to the swiper's arena view and the screen's challenge-area wrapper; confirmed fixed by tapping repeatedly near the tab bar with no stray swipes afterward.

## Hooks pattern — corrected again

The hooks rewrite above (removing the generic `useFetch`) still wasn't quite right: each hook kept an internal `useEffect` that fetched on its own mount, plus an `alive` ref to guard against setting state after unmount. Shown the actual wanted shape directly via a hand-edited `useCollectionQuery.ts`/`collection.container.tsx`: the hook exposes one **named** action (`fetchOwnedCards`, not a generic `refetch`) and does nothing on its own; the container calls that action explicitly in its own `useEffect(() => { fetchX(); }, [])`, and the container (not the hook) is where `error` gets checked. Applied the same shape to `useHomeDataQuery`/`home.container.tsx` and to `useServerDate`/`AppHeader` for consistency. Documented as the exact query-hook contract in PLAN_README.md so it doesn't drift a third time.

## UI polish pass

First read "no border, no shadow, no border radius" as an instruction to strip those — flattened the tab bar and the card face accordingly. That was backwards: the actual complaint was that the UI *looked* flat and lacking definition, i.e. no border/shadow/radius was *visible*, and the ask was to add tasteful versions of all three, not remove them. Corrected: the card now has a soft drop shadow on an outer un-clipped wrapper (shadow would otherwise get clipped by the inner view's `overflow: 'hidden'`, needed to round the image/footer), plus its hairline border and radius restored; the tab bar has its top border and a subtle upward shadow restored. Checked `collection.view.tsx` for the same issue: nothing to adjust there yet, since it has no card-styled elements until M5 adds the actual grid.

Asked for the game type (One Piece / Pokémon) to be visible on the card — added a small badge over the top-left corner of the art, mapping the raw `game` field (`onepiece`/`pokemon`) to a display label.
