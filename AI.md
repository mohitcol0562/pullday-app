# AI usage

Logged as the build goes, per the assignment's ask for honesty about where AI was used.

## How AI was used in this project

To be direct about scope: AI was used as an implementation tool, building to architecture, UI, and logic guidelines that I set and enforced throughout — not as an autonomous author of the app.

- **I defined the architecture and the coding conventions myself**, as a standing set of rules AI had to build to rather than invent on its own: the `ApiClient` interface boundary (so the mock layer is a one-line swap for a real backend later), the Zustand store shape, the `SCREENS` enum/typed navigation, the `.container/.view/type/styles/utils` per-screen folder split, and the query-hook contract (a hook owns its own `data`/`error`/`isLoading` state and exposes exactly one named fetch action; the container, not the hook, decides when to call it). These are documented as the standing rules in `PLAN_README.md`, and every screen built after they were set follows them without exception.
- **I set the UI guidelines.** A single flat palette with no theme system was a deliberate scope cut, not a default — and within that constraint, cards and chrome (the swipe card, the tab bar) are required to still read as physically distinct via a hairline border, a soft shadow, and rounded corners, rather than looking flat. I caught and reversed a first pass that stripped this instead of adding it (see below). The swipe-direction mapping (left/right/up → common/rare/holo), the game-type badge, the safe-area handling per screen, and the per-image loading state are all guidelines I specified, not choices AI made on its own.
- **I set the logic guidelines**, independent of implementation detail: real card data instead of synthetic fixtures from day one, a day boundary that will be computed server-side from a trusted clock rather than client time (the actual root cause of the shipped app's streak bugs), idempotent challenge generation, and the build order itself (swipe → collection → streak → freeze, core loop before monetization, backend after the app proves out against mocks).
- **AI's role was writing to that spec.** Small, self-contained UI pieces — the swipe-gesture card, the SVG tab icons, the price-history sparkline chart, per-thumbnail loading states — were built by AI against a clear brief. Once the conventions above were set, the repetitive follow-on work (wiring a new screen to `ApiClient`, adding a query hook, adding a mock endpoint) was also done by AI, but strictly *to* those already-decided guidelines, never inventing a new pattern per screen.
- **Where AI's output didn't match a guideline I'd set, I caught it and had it corrected** — the hooks pattern and the container/view split both needed this (see below), and the corrected shape was written back into `PLAN_README.md` so later work doesn't drift from it again.
- **I verified every milestone on a real iOS Simulator before accepting it** — swiped through the full challenge, scrolled the real collection grid, tapped through to card detail, watched the streak timer actually tick — rather than accepting AI's output on the strength of the code alone.
- **Product and scope decisions were mine, made separately from implementation** — see "Decisions made" below and `DECISIONS.md` for the full list (what got cut, what got built first, and why).

## What I caught and had corrected

- **M0 plan** — AI's first draft assumed Expo, a single monorepo, a cloud deploy, a backend-first build order, and a theme system, none of which matched the architecture I specified. I reversed all of it: bare RN CLI, two repos, local-only backend for now, app-first against mock data, no theme system.
- **Swipe library swap (M4)** — I specified `rn-swiper-list` in the plan, but on-device testing surfaced a reproducible bug (every card past the first stayed invisible after one swipe). I had it replaced with a small custom `Gesture.Pan` implementation rather than ship something broken past card one, and verified the full 8-card flow myself afterward.
- **Container/view/hooks split reversed** — AI's first pass skipped the container/view folder split and hook-based data fetching I'd specified, as "not worth it at this scope." I overturned that on review as the wrong call for this codebase, not a style preference, and had every screen retrofitted into the full `container/view/type/styles/utils` shape I require.
- **Hooks pattern corrected twice** — AI's first attempt added a generic shared `useFetch` wrapper, which I rejected since it doesn't match my hooks convention. Its second attempt had each hook auto-fetch itself on mount via an internal `useEffect`, which I also rejected. I specified the exact shape directly: the hook exposes one named action and never calls it itself; the container calls it explicitly and is where `error` gets checked. That contract is now documented in `PLAN_README.md` as a standing rule.
- **UI polish misread** — my instruction ("no border, no shadow, no border radius") was first implemented backwards, flattening the card and tab bar, when the actual guideline was the opposite: these elements need visible depth, and I'd flagged its absence as a defect. I corrected the misread and had it fixed to match my intended look.
- **Real data over fixtures** — I directed the switch from generated placeholder cards to the assignment's real `data.sql` (~2,000 cards) and provided the source link once it was located; AI wrote the one-time parser. One real parsing gotcha it hit: the file has 10 separate `INSERT` statements, not one, which broke a first-pass regex.
- **A Metro bundler issue** — splitting the real card data across two files (`data/cards.ts` → `mock/cards.ts`) caused a deterministic crash on cold launch with no explainable import cycle. Root cause not fully pinned down; fixed by collapsing into one file. Noted as a known unknown rather than papered over.
- **CardDetail safe-area miss** — the one screen that didn't get the safe-area guideline applied to every other screen; its back button rendered under the notch. I caught this during M5 verification and had it fixed the same way as the rest.
- **Simulator automation flakiness (M5/M6 testing)** — plain taps stopped registering on standard buttons mid-session while swipe gestures kept working; a tooling issue, not an app bug, worked around with a full rebuild/relaunch and the `touch_path` action instead of `tap`.

## Decisions I made (not AI)

Full list and reasoning in `DECISIONS.md`. Summary: what to build first (swipe → collection → streak → freeze, core loop before monetization), what to cut for the time box (no theme system, no dev-menu time travel, binder and win-back deferred as named stretch items), the two-repo tradeoff against the brief's literal "one repo" wording, and sourcing the real `data.sql` instead of continuing with synthetic fixtures. These are the judgment calls the brief says it's grading, and they're mine — product and scope decisions, not things a model decided on its own.
